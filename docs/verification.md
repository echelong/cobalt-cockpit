# Discovery, decisions and goal check

> Part of the [Cobalt Cockpit documentation](README.md). This text was moved here from the root README when the README was restructured for v0.6.0; the wording is unchanged unless a sentence says otherwise. Overview: [Verification Readiness](../README.md#verification-readiness).

The read-only view of what stands before DONE, `/cockpit ready`, is described in the README; the six gates and the goal check it reports on are the ones on this page. What a DONE claim rests on, and what it does not claim, is at the end: [What DONE rests on](#what-done-rests-on).

Added in v0.5.1. It is Cockpit's own heuristic, not an Anthropic workflow or endorsement, and it adds no model call: the level comes from deterministic rules over the prompt, the files the host saw edited and the consultation grounds Cockpit already reads. A router (NobodyWho or JEV) may still advise on routing; it cannot lower a level, skip a gate or waive a consultation.

| Level | When | What changes |
| --- | --- | --- |
| `LIGHT` | A typo, a label, a rename, a question, a single obvious edit | Nothing is added to the prompt. No questions, no record. Progress and gates apply as before. |
| `STANDARD` | A change request, a feature, real debugging, three or more files edited | One short line once: state the objective and acceptance criteria, name only unknowns that change the implementation, assume safely otherwise, record consequential choices, check the goal before DONE. |
| `DEEP` | A migration, authentication, payments, concurrency, data integrity, architecture, or a security or architecture consultation ground | A longer line once: establish the architecture, name only the risk categories that apply, compare approaches. Any Opus consultation still goes through `swarm consult` and its admission rules. |

A level only goes up during a task, and each level's guidance is given once. The progress tool gained three actions: `discover` (objective, acceptance criteria, material unknowns, relevant risks), `decide` (one decision) and `align` (the goal check). `/cockpit discovery` shows the state:

```
COBALT / DISCOVERY
LEVEL / STANDARD
GOAL / Implement booking cancellation
UNKNOWNS / 2 unresolved
DECISIONS / 1 recorded
ALIGNMENT / PENDING
```

**Decisions.** A record holds a problem, the chosen approach, alternatives with the reason each was rejected, trade-offs, evidence and a status (`provisional`, `verified`, `revised`). Cockpit stores what the model reported and nothing else: an alternative without its reason, or a `verified` decision without evidence, is refused rather than filled in. Records are redacted for credential shapes before they enter task state or the Run Ledger, bounded (12 per task, 64 per ledger, detail dropped before records when the 384,000-byte budget is tight) and not required for LIGHT work. The ledger also keeps one entry per task saying which level was chosen and why, in short codes, with no prompt text. Cockpit never creates `DECISIONS.md` or `CLAUDE.md`; `/ledger export decisions` prints Markdown for you to paste.

**Goal check.** A coding task above LIGHT cannot read DONE until `align` reports `ALIGNED`. Explicit acceptance criteria are required: with none declared the task shows `CRITERIA / MISSING`, `ALIGNMENT / BLOCKED` and DONE is refused, and Cockpit never invents criteria or evidence. Each criterion (stable id, meaningful description) needs its own `met` entry with evidence that names an observation (a quoted output, a file, a number); generic evidence such as "works" or a restatement of the criterion is refused, and the basis is recorded as `reported`, never as independently verified. Evidence goes stale, and criteria return to unevaluated, on edits (main or helper), a plan or replan, a new or revised criterion, a failing gate or a reopened unknown; read-only activity does not. Besides that, nothing reported missing, no unknown still open, every earlier milestone done, no blocker and every required gate passed. Passing tests are one input, never the whole. `PARTIAL`, `BLOCKED` and `UNKNOWN` are recorded and do not complete the task. Editing files (by the main session or a helper), failing a required gate or milestone, a new criterion or open unknown, or a new plan afterwards takes the check back. `ALIGNED` is refused before a plan exists, and a read-only plan whose edits are observed (`Edit`, `Write`, a Bash edit diff, a helper's edit) and that reaches a level above LIGHT is held for the goal check, though its gates stay not applicable. A plan restart cannot lower the level a task reached. The result is a hold on the existing progress model (the task stays UNVERIFIED below 100%), not a second percentage. LIGHT, read-only and operator-pinned LIGHT tasks, and tasks stored before v0.5.1, are never held by it. A pin of `light` waives this check for the rest of the session, for every later task, until you set `auto`; it changes only this check and the guidance: mandatory Opus consultations and the six gates are unaffected.

**After DONE.** For work the goal check applies to (a coding task above LIGHT), a change to the implementation takes completion back, deterministically, whether or not the model remembers to reopen the task: the goal check returns to PENDING, every criterion evaluation is cleared, and each gate that had passed goes back to pending ("stale"). The stored task is settled at once, so the status stops reading DONE. Fresh gate results and a fresh `align` with new evidence restore DONE. Reads, searches and commands that change nothing do not, and neither does staging, committing or stashing, because the fingerprint is of file contents against the commit it was taken against. A change is seen from: an `Edit` or `Write` result (main session or a helper), a Bash edit diff, a plan or replan, and, for everything else, a fingerprint of the git working tree: taken when `ALIGNED` is accepted and compared after each later tool call and before each progress call, and taken again when gates are recorded, so `ALIGNED` is also refused when the tree changed between the checks and the goal check. `NotebookEdit`, MCP filesystem writers and shell commands that rewrite files are caught by what they changed, never by their name. Measured cost of one fingerprint: 14-16 ms in a 5-100 file repository, 50-57 ms in 2,000 and 30,000 file repositories with 5 modified and 150 untracked files, about 100 ms with 1,500 modified files. It runs only while a goal check stands, once per tool call. Returning to automatic classification with `/cockpit discovery auto` never lowers a level the task has reached.

**Limits.** The completion gate is a hold on the progress model, not a proof of correctness:
- The level is a heuristic over words and file names (the full prompt text and the plan's goal), so it can misjudge a terse or oddly worded prompt in either direction; pin it with `/cockpit discovery`. An explicit pin of `light` is the operator's choice and waives the check; it is shown as an operator pin.
- Only prompts typed in the composer, or sent by the bridge or the SDK, are classified (classifying grants nothing; commands that change protected state accept only the composer and the bridge). A prompt from another origin leaves the stored prompt as it was, and a task that never receives a classifiable prompt starts at LIGHT until the plan's goal, the files edited or the model's `discover` raise it.
- A model that never calls the progress tool has no milestones, no criteria and no gates: the task stays at 0% and is never held or shown DONE. Cockpit cannot stop a claim of "done" made only in prose; after two edited files it reminds once.
- Criteria and evidence are checked for form only: present, individually evaluated, not generic, naming a file, quote or figure, not shared between criteria. Cockpit cannot tell whether a criterion is a good one or whether the evidence is true; evidence is recorded as `reported`, never as independently verified.
- Mutation coverage: edits made through `Edit`, `Write` and Bash edit diffs are observed directly. Other writers are observed only through the git working tree, so a change is missed when the project is not a git repository or has no commit yet, git does not answer in time or its output is cut short, or the tree cannot be measured safely (a FIFO, device or oversized file where Git would read it). Since v0.6.4 a goal check made in a Git repository that cannot be measured is recorded as UNKNOWN with the reason, never ALIGNED; only outside every Git repository is ALIGNED accepted without a fingerprint, and it is then shown as UNPROTECTED, the file is git-ignored or outside the repository, a tool changes a file and changes it back before the next observation, or more than 2,000 files differ from the commit. A write by a person or another program between calls is treated like any other change. Output of the test command that lands in unignored files after `ALIGNED` also reads as a change. Tool permissions and ownership are unchanged: nothing here allows or denies a call.
- The "After DONE" protection applies to goal-checked work only. A LIGHT task, a read-only plan whose edits are not observed by `Edit`, `Write` or a Bash edit diff, and a task stored by v0.5.0 are not goal-checked: they keep their gates and DONE after later edits. Giving a coding request a read-only plan, or phrasing it as a question, can keep the level at LIGHT.
- The fingerprint hashes the raw bytes of regular files (no git filters), the text of symbolic links and the kind of FIFOs, sockets and devices, which it never opens (since v0.6.4); it ignores file-mode changes of untracked files. A submodule or a nested repository among the changed files makes it unavailable, and build or test artifacts that are not git-ignored read as changes. Checks that passed before a task became goal-checked, or while its working tree could not be measured, were observed on no identified tree. On `main` since the 0.6.5 version commit (not yet in a release) they do not count for the goal check: ALIGNED is refused while a required gate passes without a fingerprint, and such a pass goes back to pending at the first check observed on a measured tree instead of being taken to describe it. A command's exit 0 read where a goal-checked task's tree could not be identified is kept as an unqualified observation (a pending gate with its evidence), and the Stop guard records an exit 0 on a tree it cannot identify the same way: in the Run Ledger, and as a pending TEST gate.
- An accepted goal check, and the checks it rests on, are withdrawn when a tree that was measured can no longer be measured (since v0.6.4): a failed measurement is never taken for an unchanged tree. A measurement cut short only because a file changed while it was read is taken once more first. The limits and what they do not cover: [SECURITY.md](../SECURITY.md#working-tree-measurement-limits).
- Evidence checks are weak by design: any figure satisfies "names a figure", restating a criterion is an exact-text test, and evidence that is made distinct by appending a tag still counts as distinct.
- Decision records and discovery entries in the Run Ledger are keyed by task number, which restarts after `/cockpit reset` or `/clear`; an older task's entry can be replaced by a new task with the same number.
- A legacy v0.5.0 task that is nearly done becomes goal-checked if `discover` or `/cockpit discovery <level>` is used on it.

## What DONE rests on

> On `main` since the 0.6.5 version commit; not yet in a release. The manifest still reads 0.6.5. An installation of 0.6.5 made before these commits shows the older labels: `STATE / VERIFIED` for a finished task, `verified` in `/cockpit flow` and `VERIFIED by the commander` in `/cockpit agents`. It also lacks two behaviour changes, which are rules rather than labels. First, an exit 0 on a working tree that cannot be identified is not a pass (the fingerprint limit above, and the Stop guard below). Second, a Stop-guard completion counts only under the trust in force (below).

**DONE is a task-completion status.** It means every milestone is complete, every required gate is pass or n/a, the goal check is `ALIGNED` where it applies, no Opus consultation is waiting to be adjudicated and, under `stopGuard: ENFORCE`, the Stop guard has completed its check for this task and tree. It is not an independent verification of the work and it is not a security attestation. Where a task reads DONE, Cockpit also says what the claim rests on, in the HUD's status word (`DONE · PROVISIONAL_CHECKED`), the Mission Control pane, `/cockpit flow` and the progress tool's reply. `/cockpit ready` prints its `COMPLETION` line for every task. Before DONE, that line reads `UNKNOWN_INVALIDATED` with the reason, for example `DONE is not claimed by the recorded task`. The `/cockpit flow` line and the progress tool's reply end `not a security attestation`. `/cockpit ready` appends the same words, but cuts its line to the terminal's width, so they can be cut off. These are the five states a claim can be in:

| State | What it means |
| --- | --- |
| `SELF_REPORTED_UNCHECKED` | Reported, with no applicable check recorded: a gate pass Claude reported, a DONE that rests only on milestones and n/a gates, or a DONE with at least one required pass that was only reported |
| `PROVISIONAL_CHECKED` | An applicable check ran and its result was observed: a command whose result Cockpit read, or the Stop guard's record of its own passing check. This is limited evidence: an exit 0 shows that a command passed on the tree it ran on, not that the work is correct, and every limit on this page still applies |
| `UNCHANGED_UNCHECKED` | The Stop guard measured the working tree, found it unchanged since the task began, and ran no check |
| `PROVENANCE_UNKNOWN` | A pass recorded as automatic carries no result line, so the check behind it cannot be attributed. Nothing in it says the result was withdrawn |
| `UNKNOWN_INVALIDATED` | The evidence does not hold. This covers a pass that is stale, unqualified (observed on a tree that could not be identified) or has no usable source, a required gate not settled, a task the Stop guard holds, a guard record for another task, and a task that claims no DONE |

The weakest evidence decides. One stale, unqualified or sourceless required pass makes the claim `UNKNOWN_INVALIDATED`. Otherwise, one pass with no recorded result makes it `PROVENANCE_UNKNOWN`. Otherwise, one pass that was only reported keeps it unchecked: `SELF_REPORTED_UNCHECKED`, or `UNCHANGED_UNCHECKED` when the Stop guard found the tree unchanged. Under `stopGuard: ENFORCE` the guard's record counts too. With no guard record for the task, the claim is `UNKNOWN_INVALIDATED`. A recorded passing check, or an unchanged tree, is `PROVISIONAL_CHECKED` when every required pass was read from a command; a recorded passing check also gives `PROVISIONAL_CHECKED` when no required gate passed. A sixth name, `SECURITY_ATTESTED`, is reserved, and no code path produces it. A passing SECURITY gate carries `not a security attestation` at the end of its gate line.

**Gate lines.** In `/cockpit ready` and the Mission Control pane, each pass names its state: `CODE pass · SELF_REPORTED_UNCHECKED · reported by Claude, not read from a command`, or `TEST pass · PROVISIONAL_CHECKED · read from a command`. A self-reported pass still satisfies its gate, as it always has. The label says what it is; it does not change what the gate accepts.

**Unknown provenance is not revocation.** `PROVENANCE_UNKNOWN` says a pass names an automatic source but keeps no result that would support it; nothing in it says the result was revoked. `UNKNOWN_INVALIDATED` is the state for evidence that is stale, unqualified or otherwise no longer holds. A Run Ledger checkpoint keeps each gate's state but not its source, so `/ledger` shows a stored pass as `provenance unknown (source not retained)` and marks the checkpoint's gates as historical state. That does not mean the pass was withdrawn.

**A stored Stop-guard result is history.** `/cockpit ready` shows the guard's record of a passing check with a note. The note says the stored record is historical, and that the view does not revalidate current script trust or tree identity. In the completion state it counts as an observed check (above). Showing an old pass is not a fresh check of current trust.

**The trust in force** (a behaviour change, not a label). Under `stopGuard: ENFORCE`, completion is checked in the Stop guard, at session start, at each prompt, and when a turn ends without an answer. At each of those points, a completion the guard verified counts only while the trust its check ran under is still in force. The check must have run for the same script and project, on the same bytes and after the current enrolment, and the script must still be enrolled and match its pin. A typed `/cockpit guard untrust` or a new enrolment withdraws such a completion for the current task at once, unless its check record shows another script's verifier. A changed script or pin is found the next time completion is checked. Withdrawal removes the guard's record, makes the TEST pass its check wrote stale and starts the goal check over. The Run Ledger keeps the record of what ran. A check that exits 0 on a tree the guard cannot identify does not complete the task. It is recorded as a pending TEST gate with its evidence, and for a goal-checked task, passes observed on a measured tree become stale.

**Commander reports.** A verdict the commander records with `swarm action verify` is its own judgment, not a check Cockpit ran. `/cockpit agents <task>` shows it as `commander report PASS · SELF_REPORTED_UNCHECKED` (or `FAILED`, `UNKNOWN`). The `COMMANDER REPORTS` row of Mission Control's ORCHESTRATION section counts the passes under `SELF_REPORTED_UNCHECKED`. For an Opus consultation's verdict, the consultation lines in that section and in `/ledger` say `commander report` with `SELF_REPORTED_UNCHECKED`, and `/cockpit stats` counts `commander report pass`. Some places keep the older word for the same report: the route line of `/cockpit agents` (`verified`), a swarm task's row in `/ledger` (`verification pass`) and the `/cockpit stats --json` and `--csv` metric names (`verified_pass`, `verified_fail`). `/cockpit ready` lists completed agent results that have no commander-approved PASS. Only the wording changed: a verdict unblocks the same things it did before. A returned Opus consultation is a recorded response. For a release, only a GO that the main session confirms against the architect's own DECISION line (`release_outcome`) clears the release ground. A NO-GO, or a response not yet adjudicated, is not an approval.

**What the labels do not change.** The states and labels in this section are reporting only. Gate eligibility, the Stop guard's verdict, the `ALIGNED` rule, release decisions and what the Run Ledger stores keep their rules, and no label adds or lifts a hold. The two rules above that do change behaviour are the unidentified-tree rule and the trust in force: each can keep a task from reading DONE. None of this changes how the working tree is measured. So it does not resolve the two open findings about that measurement: how nested repositories and submodules are handled (tracked as F01), and the resource bounds of listing a working tree's entries (tracked as A2). Both remain open. [SECURITY.md](../SECURITY.md#working-tree-measurement-limits) lists the measurement's current limits.
