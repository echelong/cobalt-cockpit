## Orchestration

**Observation is the public default.** With `orchestration: false`, Cockpit observes your existing Claude Code activity without enforcing model routing, subagent budgets, Fable blocking, or subscription-only authentication. The bundled explorer/researcher/worker/reviewer agent definitions use Sonnet 5.5; scout/utility use Haiku 5.5.

Set **`orchestration: true`** to enforce the Opus/Sonnet/Haiku policy, independent pool resource budgets, and explicit task ownership within a session ([limits](#what-task-ownership-does-and-does-not-guarantee)). Orchestration does not by itself block Fable outside routed work. **`blockFable` is a separate opt-in**. **`cobaltStrict`** is an optional stricter preset that also blocks Fable/external advisor selection and requires subscription-style authentication. These models must be available to your account; Cockpit cannot grant model access.

The strict preset takes precedence over individual enforcement switches. NobodyWho remains optional: Cockpit observes its local receipts if configured and does not install it. It sends the local router a request only in a session where you selected a router with `/cockpit router`.

### Elastic execution

Opus remains the single commander: architecture, planning, decomposition, integration, escalation decisions and final verification. Sonnet engineers substantial bounded changes and independent reviews. Haiku scouts repositories and processes extractive, repetitive work. Small or tightly coupled work stays in the main session.

The `swarm` tool records bounded assignments before spawning. Each assignment carries a task ID, parent, tier, semantic role, objective, scope, dependencies, resource ownership, read/write mode and spawn reason. Include the exact `[task:ID]` marker in the Agent description. Queued tasks wait for resource capacity; blocked tasks wait for dependencies; within one session, intersecting write scopes are serialized ([limits](#what-task-ownership-does-and-does-not-guarantee)). Read-only scopes may overlap. Scoped agents use Read/Grep/Glob for inspection and Edit/Write for changes. Shell or custom tools require exclusive wildcard ownership, with one exception: read-only Git inspection. A task that owns named paths can run `git diff`, `show`, `log`, `status`, `grep` and `ls-files` on those paths (one plain command, options from a fixed list, revisions proved to be commits, an explicit `--` and literal paths inside its scope); a wildcard read-only task keeps a wider set of safe Git inspection commands. In both cases the command that runs is rebuilt from its parsed words behind safe flags, and Claude Code's own permission rules still apply to it. The exact rules: [implementation-v0.6.1.md](implementation-v0.6.1.md#scoped-read-only-git-inspection). Path canonicalization fails conservatively to wildcard when unavailable. Resource budgets replace the old three-agent ceiling; AUTO provides backpressure rather than uncontrolled fan-out.

### What task ownership does and does not guarantee

Task ownership is an admission rule Cockpit applies inside one session, while its hooks run. It decides what Cockpit admits next. It does not stop an agent, and it is not a lock enforced by Claude Code or by the file system. Nothing here is native fencing, effect drainage or verified termination.

The observations below ran on Claude Code 2.1.296 and 2.1.316 on Linux, on commit `7d52ab2` or released 0.6.5 where they say so, and otherwise on the code that introduced the behaviour they describe. It does not describe a future release.

**Which version does what.** Installing the plugin gives 1.0.0. The last column is the code in 0.6.6 from the change that followed `7d52ab2`, which 1.0.0 keeps; 1.0.0 also refuses a read claim that cannot be kept narrow instead of widening it to `*`. The v0.9.0 Cobalt Recall research spike remains fixture-only, and 1.0.0 changes none of the behaviour in this table.

| Behaviour | Released 0.6.5 | `main` at `7d52ab2` | `main` after `7d52ab2` (in 0.6.6) |
|---|---|---|---|
| `/clear` while an agent runs | New exclusive task admitted, overlap seen on both hosts | The same | **The same. Not fixed** |
| A detached child after a stop | Not run on this version | Not run on that commit. With a test plugin and no Cockpit, it outlived the stop | **It outlived the stop on both hosts. Not fixed** |
| A refusal from a hook after dispatch | Releases the claim (read from the code, not run) | Released the claim, though the host may have started the agent, on both hosts | Holds the claim |
| `SendMessage` to a finished or stopped agent | Not run on this version | On 2.1.316, left a whole-project claim stuck | On 2.1.316, refused, and no claim opens. On 2.1.296 no event is raised, so this refusal is not reached |

The last column's `/clear` and detached-child results were run with Cockpit loaded, on the code of that change. Neither change gives native fencing, effect drainage or verified termination. Only the operational rule below covers `/clear`, and Cockpit does not enforce it.

**What the `main` behaviour costs.** A refusal after dispatch is held for the rest of the session, however true the refusal was. While it is held, commander shell and custom tools and overlapping writes are refused, unless the task is an Opus task, and no command releases it. A plugin that refuses spawns beneath Cockpit therefore stops further shell work while the claim is held. With orchestration on, `SendMessage` cannot continue a finished or stopped agent on 2.1.316, so further work needs a new task. These costs are the price of keeping ownership when an agent may have started.

**Do not use `/clear`, switch sessions, or replace overlapping tasks while an agent is running or ownership remains uncertain.** That includes `/new` and `/reset`, which are the same command, `/resume`, `/branch`, the option to clear context when approving a plan, and another process on the same session. This is an operational rule for people. Cockpit does not enforce it.

**What ownership does.** Within one session, Cockpit refuses a new admission that overlaps a held claim when either side writes, and refuses new calls from an agent with no active bound ownership. When a spawn's outcome is uncertain, it keeps the claim through stalls, cancellation requests and a restart of that same session, and shows it as `UNCERTAIN`. No command releases a swarm claim: such a claim ends only on a verified agent id followed by a reported end, or, before dispatch, on a positive no-start. `/clear` and a new session do not release a claim; they leave it behind, which is the gap described below.

**What it does not do:**

- **Ownership does not survive `/clear`.** `/clear` gives the session a new id. Background agents keep running, while Cockpit's record of who owns what is lost, so a new task can be admitted over a running one. This was observed on real hosts: Claude Code 2.1.296 and 2.1.316 on Linux, commit `7d52ab2`, one interactive run per host, with no third-party plugin and no failed spawn. A second run per host on the same commit repeated it, and released 0.6.5 (commit `7a7ca1a`) overlapped the same way in one further run per host. Agent A owned the whole project for writing and had a Bash command running. After `/clear`, a new task was admitted with the same whole-project ownership, and the two Bash commands ran at the same time for about 4 seconds in each of these runs. Those commands were test commands, a sleep ending in a marker file, so the run shows that overlap was admitted, not that files were damaged. On `7d52ab2` Cockpit refused A's next model request; on 0.6.5 that request went through. Neither touched the command already running. An uncertain claim is dropped the same way: after `/clear`, a held refusal no longer held commander Bash or a new task, one run per host on 2.1.296 and 2.1.316. Cockpit's per-session swarm budgets are counted from the same record, so they restart too; that was read from the code, not tested.
- **Other session changes should be treated the same way.** `/resume` to another session inside a running process changed the session id and reset session state, as `/clear` does; on 2.1.296 and 2.1.316 this was observed with a test plugin, and an overlap through it was not run. `/branch` changed the session id and reset session state too, one run per host. Approving a plan with the "clear context" option, which needs the `showClearContextOnPlanAccept` setting and a written plan, reset the session on both hosts; with a Sonnet agent running, Cockpit's general hold on commander tools refused the plan-approval tool and no approval dialog appeared. From the code, that hold does not apply to an Opus task or to an agent Cockpit does not track. `/compact` kept the session id and session state in a short test conversation.
- **Ownership does not cross sessions.** Records are kept per session id, so a new session does not see another session's claims. A second process that resumes the same session does read them.
- **A reported end is not proof that effects stopped.** Cockpit ends a task's ownership when Claude Code reports the agent's turn ended. Measured with a test plugin, not Cockpit, one run per host: a stopped agent's Bash command had started four test children. `TaskStop` returned, `turn.complete` reported `aborted` and the agent list showed `killed`. A child started with `setsid -f` then wrote its marker file 4.93 to 4.97 seconds after those signals. The foreground child, a `nohup` child and a child ignoring SIGTERM wrote nothing. So a deliberately detached process can outlive every signal Cockpit sees. How often that happens in real work was not measured.
- **`killed` is not final, and it is not the same as exited.** With a test plugin, on both hosts, a message resumed a `killed` agent under the same id. In another run, with Cockpit loaded, one second after the stop, 2.1.296 refused the same step because the agent's previous run had not exited. That depends on timing. Cockpit refuses a retired agent's further model requests while its hooks run.
- **A host crash did not stop the test children.** After SIGKILL of the host, one run per host, all four test children finished and wrote their files about 6 seconds later.
- **A refusal from another plugin is not a no-start.** A hook beneath Cockpit that calls `next` and returns `{ deny }` before `next` answers may leave an agent that the host started. Observed on both hosts with a test hook of that shape: in those runs no model request from that agent was sent. Cockpit cannot tell that from a true refusal, so it holds the claim in both cases, as described [below](#routes-waves-and-cancellation). A hook that denied after `next` had answered was ignored by the host on both hosts, and the agent's id stood.
- **Some holds do not clear.** A refusal after dispatch holds its claim for the rest of the session, and a claim that could not be settled because storage failed is held too. If a session's stored ledger is lost, a finished task can return as an uncertain claim; that was tested with a simulated host. Within the session, both keep the claim. The only way on from such a hold is to leave the session, which is what the rule above warns against: a new session leaves the claim behind, only because of the cross-session gap above. `--resume` of the same session brings the claim back. That is a person's decision to make after inspecting what the agent was doing, knowing that nothing shows earlier work has stopped and that a process can outlive its host.
- **The rules need the hooks.** If Cockpit is unloaded or disabled, none of this is enforced.

### Routes, waves and cancellation

Each assignment also records the tier Cockpit's own route would suggest for it, read from the mode, the role's class, a named effort and the wave. It is advice: the commander's tier is the one admitted and spawned, the reply to `assign` names a differing suggestion, and `/cockpit agents` shows suggested, requested, admitted, spawned, completed and verified per tier. Nothing is spawned or re-tiered by it ([how it is derived](implementation-v0.6.1.md#what-changed-for-delegation)).

**A refusal after dispatch holds ownership.** If a hook beneath Cockpit answers `{ deny }` after Cockpit has dispatched, Cockpit cannot tell a true refusal from an agent that started anyway, so it treats both as possibly started. A true refusal reaches the model; when the agent did start, the model was told it launched. Either way the task stays `reserved`, shown as `UNCERTAIN` on the HUD line when the HUD has room (`SWARM: 1 UNCERTAIN · ownership retained · commander effects held · /cockpit agents`). `/cockpit agents <task>` gives the refusal, what is held and what ends the hold. This has a real cost when another plugin refuses spawns: each refusal holds that task's resources, and while it is held commander shell commands and custom tools are refused, whatever the task owned, as are overlapping writes, unless the task is an Opus task. Reads continue. No command releases such a claim. Only a verified agent id and its reported end do. The only way on is to leave the session, which is a person's decision: a new session leaves the claim behind and shows nothing about whether the agent ran, and `--resume` of the same session brings the claim back. `/clear` also drops the claim, so it is no safer a way out.

**A resume is refused.** With orchestration on, `agent.spawn` for a resume is refused whatever the state of the agent or its task, because nothing shows that agent may safely run again. On Claude Code 2.1.316, `SendMessage` to a finished or stopped agent then returns `success: false` with the reason, no claim opens, and commander shell work continues. Further work needs a new task. A new task that overlaps a task Cockpit still holds is refused until that agent's end is reported, and if no end is ever reported nothing clears it; unit tests cover this, not a real host. `SendMessage` to a running agent raised no such event and was queued as usual on both hosts. 2.1.296 raises no event for a resume, so this refusal is not reached there: `SendMessage` reports that it is resuming the agent, and no further model request from that agent reached the test model. These are one run per case on each host. Teammates were not tested; a teammate resume that reached this hook would be refused.

Run waves are reconnaissance → engineering → review → integration → verification. Waves are observable phases; they do not replace dependency checks. Haiku may escalate reasoning to Sonnet; Sonnet escalates ambiguity, architecture and high-risk changes to Opus. Handoffs preserve objectives, discoveries, evidence, unresolved questions, risk and next actions. Escalation is distinct from ordinary completion. Agents return concise conclusion/evidence/change/check/uncertainty artifacts; commanders verify claims independently. The commander's verdict, recorded with `swarm verify`, is itself a report, not a check Cockpit ran. In 0.6.6, `/cockpit agents <task>` shows it as `commander report PASS · SELF_REPORTED_UNCHECKED`, where an installation of the 0.6.5 version commit shows `VERIFIED by the commander`. Mission Control's `COMMANDER REPORTS` row counts passes under `SELF_REPORTED_UNCHECKED`. Some places still use the older word for the same report, such as the route line's `verified` count and a task's `/ledger` row. Only the wording changed: a verdict unblocks the same things as before ([What DONE rests on](verification.md#what-done-rests-on)).

`/cockpit` groups observed tiers, compresses pools larger than eight agents and reports task progress, queue, blockers, ownership conflicts and escalations. While a task is blocked, quiet (the swarm's stalled mark: no activity observed for the threshold) or escalated, the HUD adds one static line, `SWARM: 2 BLOCKED · 1 QUIET 5m+ · 1 ESCALATED · /cockpit agents`, read from the Ledger the render already holds; with none of those there is no line ([details](implementation-v0.6.1.md#the-swarm-line-on-the-hud)). The Activity Field retains its crawler/spine identity and aggregates utility pools. The Run Ledger and replay explain assignment, spawn reason, wave, completion, escalation and verification. Escalated results remain unresolved after their host stops; the commander uses `swarm resolve` with evidence before dependent work can proceed. Queued dispatch stays under the commander through Agent, rather than automatic spawn loops. Active cancellation suppresses further model and tool actions while Cockpit's hooks run, and retains ownership until the host reports that the agent's turn ended. That report is not proof that effects stopped ([limits](#what-task-ownership-does-and-does-not-guarantee)). Cockpit itself never stops an agent. For a running pre-v0.2 agent with unknown ownership, the commander explicitly assigns its scope then uses `swarm adopt` with the observed `agent_id`; until then further agent tool effects are held. Older ledgers default to an empty swarm; unavailable telemetry stays unknown. NobodyWho boundaries remain read-only.

```text
Opus 5.5          — commander / integration / final verification, at your /effort
  ├─ Sonnet 5.5     — 0..N bounded engineering and review, effort per task
  └─ Haiku 5.5      — 0..N scouts and utility work, effort per task
       escalation → Sonnet → Opus
Cobalt Cockpit — ownership / waves / backpressure / HUD / ledger / replay
NobodyWho     — local Decision / Pruning / read-only control telemetry
```

## Dynamic reasoning

Model selection and effort selection are separate decisions. The 5.5 tiers still command, engineer and scout. **You control the main Opus loop's effort; Cockpit manages the subagents'**, per task rather than fixed per tier.

- **AUTO** (default) names a level from the task: extractive inventories, classification and summaries run light; normal feature work, bug fixes and refactors run medium; complex debugging, concurrency, migrations, security analysis and high-risk architectural reasoning run high or xhigh; unusually difficult high-stakes reasoning may use max. A task that names no class falls back to its tier's baseline.
- A commander can name a level explicitly per assignment with the `swarm` tool's `effort` field (LOW / MEDIUM / HIGH / XHIGH / MAX, or AUTO). A named level wins AUTO. **MANUAL** mode instead honours the fixed per-tier levels and leaves Haiku unspecified.
- A task's level is *requested*, not guaranteed. The operator's `maxEffort` cap applies to subagents, and the host can apply its own limits. The Ledger distinguishes the requested level from the **engine-resolved** level and names a mismatch (`EFFORT FALLBACK`). This is host-resolution evidence, **not an independently captured wire receipt**. Unknown stays unknown.
- A subagent's level is set natively, on its own Agent call's `effort` parameter (Claude Code 2.1.292 or newer): one level per invocation, with no global setting for parallel agents to race on. It overrides the agent definition's `effort` frontmatter and a per-model `effortLevel` for that subagent only. The engine's own limits still win — `maxEffortLevel`, an organization's cap, `CLAUDE_CODE_EFFORT_LEVEL` and the model's support — and the level the engine resolves is what the ledger records as applied. When that is not the level asked for, the difference is named with both levels; it is never rewritten back.
- **The main loop's effort is never written by Cockpit.** A `turn.step` rewrite sits above everything in the engine's order (rewrite, then `CLAUDE_CODE_EFFORT_LEVEL`, then a session level from `/effort`, `--effort` or the model picker, then the settings' `effortLevel`, then the model's default, all under `maxEffortLevel`), and most of those cannot be seen from a plugin, so there is no way to offer a level *beneath* your own choice. The level the engine resolved is sent untouched and recorded as `engine`, with what was seen of its origin: the variable, a `/effort` typed this session, the settings, or `host` when none of those accounts for it. A cap that lowered your selection is named with both levels. AUTO and MANUAL, the `maxEffort` ceiling and every subagent launch leave it alone. With no selection of your own the main loop runs at the host's default for the model, which is not necessarily the level AUTO would name: `/cockpit version` then says what AUTO would name, as advice, and `/effort <level>` sets it.
- A subagent on an older engine, or one that no Agent call launched, gets its level from a per-request `turn.step` rewrite instead. The engine does not report that rewrite back, so there the ledger shows the level as *requested* (`request`), leaves *observed* unknown, and learns nothing about capability from the engine's reports.
- A failing task escalates one step at a time: raise effort within the tier first, then move a tier (Haiku → Sonnet → Opus). It never jumps to the top and stops at the budget rather than retrying forever.

The HUD shows the applied effort beside the model; `/cockpit version` prints the reasoning mode, the ceiling, the main loop's host-resolved level and where it was seen to come from, how a subagent's level reaches the engine, and only the capability this session has really observed.
